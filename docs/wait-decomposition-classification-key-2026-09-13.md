# 待ち分解分類を64 bitキーへ収める設計 2026-09-13

この文書は、7枚形・10枚形・13枚形の計算結果をもとに、`waitDecompositionCodes` と等価な分類を
64 bit整数で扱う方法を検討し、今後の実装方針を定める。

根拠となる実装は [Mahjong/WaitDecompositionCode.lean](../Mahjong/WaitDecompositionCode.lean)、
計算結果は [7枚形](../reports/seven-tile-report.json)、[10枚形](../reports/ten-tile-report.json)、
[13枚形](../reports/thirteen-tile-report.json) の各レポートを参照する。

## 結論

`waitDecompositionCodesKey` をそのまま64 bitへ収めることはできない。一方、このプロジェクトで
興味の対象となる分類は、4枚形・7枚形・10枚形・13枚形の各レポートに列挙された**既約分類**である。
この有限集合を対応表としてプログラムへ組み込み、各 `waitDecompositionCodes` 列へ密な整数IDを
割り当てれば、同じ同値関係を保ったまま64 bitへ十分収められる。

推奨する分類キーは次のとおりである。

1. 各レポートから `waitDecompositionCodes` 列全体を読み取る。
2. 牌数ごとにコード列を辞書順へ並べ、全牌数で一意な0始まりの密なIDを割り当てる。
3. `(牌数, waitDecompositionCodes) -> classificationId` の静的対応表を生成する。
4. 可約形は同じ待ち核集合を保つ完成面子を再帰的に除き、到達した既約形の表を引く。
5. DBには分類IDを保存する。

このIDは牌姿の完全ハッシュではなく、**既約分類の完全ハッシュ**である。同じ
`waitDecompositionCodes` を持つ既約牌姿には同じIDを、異なるものには異なるIDを返す。
4枚可約形の還元終点となる1枚単騎には、レポート由来ID 0から966の後にID 967を割り当てる。
対応表にも還元先にもない入力は、生成済みレポートと実装の不一致として検出する。

## 現行分類が表す同値関係

`waitDecompositionCodes` は、各待ち分解から具体的な牌と待ち牌を忘れ、部品種別の多重集合を
素数積へ変換した後、そのコード列を昇順に並べたものである。同じコードが異なる待ち牌から
得られた場合、その重複はコード列に残る。

同じ牌数において、2つの牌姿を同じ分類とみなす条件は次である。

```text
waitDecompositionCodes(first) = waitDecompositionCodes(second)
```

全牌数で一意なグローバルIDを使うため、新しい64 bitキー全体は `classificationId` とする。
このキーには次の性質が必要である。

```text
classificationKey(first) = classificationKey(second)
  ↔ reduceToIrreducible(first) と reduceToIrreducible(second) の分類が同じ
```

牌姿、待ち牌、具体的な分割を区別する主キーではない点には注意する。

## 現行キーが64 bitを超える理由

個々の待ち分解コードは、7種類の部品種別へ割り当てた素数の積である。標準形では部品数が
最大5なので、個々のコードは十分小さい。

現行の `waitDecompositionCodesKey` は、実現可能な素数積792種類を0始まりの順位へ変換し、
コード列全体を792進の双方向基数記法へ埋め込む。この方法は可逆で衝突しないが、長さ $n$ の
列に約 $n\log_2 792$ bitを使う。コード列が長くなると、分類の実際の種類数が少なくても
キーだけが急速に大きくなる。

レポートの既約分類を全行検査した結果は次のとおりである。

| 牌数 | 分類数 | 最大コード列長 | 最大キー長 | unsigned 64 bit超過 |
|---:|---:|---:|---:|---:|
| 7 | 49 | 7 | 66 bit | 1件（2.0%） |
| 10 | 199 | 10 | 96 bit | 52件（26.1%） |
| 13 | 708 | 16 | 154 bit | 386件（54.5%） |

3レポートの全行について、同じキーが異なるコード列を表す衝突はなかった。問題は一意性ではなく、
実現可能性を考慮せずコード列を一般的な可逆整数へ埋め込んでいるために生じるサイズである。

## 64 bit化が可能である根拠

任意の792種類の任意長多重集合を64 bitへ入れる必要はない。対象は、麻雀の合法牌姿から
実際に生じる分類だけである。

13枚の合法牌姿総数は98,521,596,000であり、$2^{37}$未満である。異なる分類数は異なる牌姿数を
超えないため、13枚形の分類集合全体にも高々37 bitの密なIDを割り当てられる。7枚形・10枚形を
合わせても同じ64 bit上限には十分な余裕がある。

今回の対象である既約分類は、4枚形11種類、7枚形49種類、10枚形199種類、13枚形708種類である。
これら967種類と1枚単騎の還元終点1種類を単一の名前空間へ置いても10 bitで足りる。

## 推奨方式: レポートから生成する静的対応表

### 対応表の単位

対応表のキーは個々の `waitDecompositionCode` ではなく、`waitDecompositionCodes` の**列全体**とする。

```text
(tileCount, waitDecompositionCodes) -> classificationId
```

個々のコードだけを小さい整数へ置換しても、可変長のコード列全体を一意な64 bit整数へ結合する
問題が残る。列全体を既約分類の有限集合から直接検索すれば、その問題を避けられる。

IDはレポートの行順から割り当てない。集計や並列実行方法の変更で行順が変わってもIDを安定させるため、
牌数ごとに `waitDecompositionCodes` を辞書順へ並べ、その順番をIDとする。対応表は手書きせず、
レポートからLeanソースまたは共通データファイルとして生成し、生成物をバージョン管理する。

現在の規模は最大でも13枚形の708件なので、単純なソート済み配列と二分探索で十分である。
最小完全ハッシュを追加してもよいが、性能測定で必要性が示されるまでは導入しない。

### 正規表現

Lean内の対応表では、既存の昇順 `List Nat` をそのままキーとして利用できる。DBや外部ファイルへ
対応表を出力する場合は、巨大な自然数ではなく次の正規バイト列を使える。

1. 現行の素数積コードを、実現可能コード空間上の順位0から791へ変換する。
2. 順位を昇順のまま、1要素2 byteの符号なし整数としてbig-endianで並べる。
3. 列長はバイト列の長さから求める。

順位は10 bitで表せるため2 byteで十分であり、13枚形で観測された最大長16でも32 byteである。
この表現は可逆であり、同じ `waitDecompositionCodes` から必ず同じバイト列が得られる。

素数積そのものは分類の意味ではなく、部品種別多重集合を一意に表すための実装手段である。
将来は各待ち分解を7種の部品個数から直接順位化し、素数積を経由しない実装へ置き換えてもよい。
その場合も、既存分類との一致を全件比較してから切り替える。

### 静的対応表の生成

対応表は次の工程で生成する。

1. 4枚形・7枚形・10枚形・13枚形レポートの既約グループを読み取る。
2. 各行の `waitDecompositionCodes` が昇順であることを検査する。
3. 牌数ごとにコード列の重複を検査し、辞書順へ並べる。
4. 0始まりの `UInt64` IDを割り当て、静的対応表を生成する。
5. 生成件数が11、49、199、708であり、1枚単騎を加えた総数が968であることを検査する。
6. レポートの全行が対応表から検索でき、異なるコード列のIDが異なることを検査する。

辞書順による採番は同じ分類集合から常に同じ結果を作れる。ただし、新しい分類が途中へ挿入されると
後続IDが変わる。生成済みIDをDBの永続キーとして運用開始した後は、対応表を版付き成果物として固定し、
新しい分類を追加する場合は未使用IDを割り当てるか、明示的なDB移行を行う。

### DBの分類辞書

DBでは、静的対応表と同じ密なIDを使う。分類辞書も保存する場合は、正規バイト列へ一意制約を付ける。

```text
wait_classification
  tile_count         SMALLINT NOT NULL
  id                 BIGINT NOT NULL
  encoding_version   SMALLINT NOT NULL
  canonical_value    BINARY / BLOB NOT NULL
  PRIMARY KEY (id)
  UNIQUE (encoding_version, tile_count, canonical_value)
```

牌姿テーブルは `classification_id` だけを外部キーとして持つ。これにより通常の検索・結合は
64 bit整数だけで行え、正規バイト列は分類登録時または整合性検査時にだけ使えばよい。

実行時に新しいIDを採番する必要はない。対応表にない値は登録せずエラーにすることで、対象が既約分類に
限定されていることと、レポート・プログラム・DBの版が一致していることを検査できる。

## 64 bit IDの範囲

DBとの互換性を優先し、符号付き64 bitの非負範囲に収める。分類ID自体を密な連番とし、
符号化方式の版は別列で持つ方法が最も単純である。

単一整数へ版も含める必要がある場合は、上位7 bitを版、下位56 bitを分類IDとする。

```text
key = (encodingVersion << 56) | classificationId
```

これでも分類IDを約 $7.2\times10^{16}$ 個保持でき、麻雀牌姿数から得られる上限を大きく上回る。
ただしDBスキーマで版を別列にできるなら、ビット分割より別列を優先する。

## 採用しない案

### 現行キーの下位64 bit

異なる分類が同じ値になるため、等価な分類ではない。採用しない。

### 通常の64 bitハッシュだけを保存する

衝突確率が低くても完全ではない。分類の正しさを要求するキーとしては採用しない。
検索用ハッシュを補助列に置く場合も、最終的な一致は正規バイト列で確認する。

### コード列の組合せ順位

コード列がソート済みであることを使えば、792進表現より小さくできる。しかし任意の長さ10の
多重集合は約75 bit、長さ16では約111 bitを必要とし、一般的な64 bit解にはならない。
実現可能な分類集合を列挙する方が、麻雀の制約を直接利用できる。

### 多倍長整数をDBキーにする

現行値をそのまま保持できるが、一般的な牌姿キーが64 bitで扱える設計との整合性が悪く、
DB間の可搬性や索引サイズでも不利になる。移行時の照合用以外には採用しない。

## 実装と検証の手順

1. 4レポートから静的対応表を生成するツールを作る。
2. 生成件数、コード列の昇順、一意性、ID範囲を検査する。
3. 対応表の検索結果を `Option UInt64` とし、対象外入力を明示する。
4. 4レポートの全既約グループについて、検索したIDから元のコード列を復元できることを検査する。
5. 同じコード列には同じID、異なるコード列には異なるIDが割り当てられることを検査する。
6. 旧 `waitDecompositionCodesKey` は移行検証用に残し、一致確認後にレポートとDBの公開キーを
  64 bit分類IDへ切り替える。

対応表の定義域は、各レポートに記録された既約分類と1枚単騎に限定する。可約形は待ち核集合を
保つ完成面子除去を再帰的に適用してから対応表を引く。複数の除去経路が異なるIDへ到達した場合は
黙っていずれかを選ばず、分類の曖昧性としてエラーにする。

## 判断

分類が64 bitへ収まらないのは分類情報量の問題ではなく、現行の汎用可逆符号化が既約分類集合の外まで
表現しているためである。`waitDecompositionCodes` を分類仕様として残し、レポートに現れたコード列全体へ
静的な密なIDを割り当てる。プログラムとDBは同じ版付き対応表を共有し、未登録値を対象外として検出する。
